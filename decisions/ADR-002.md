# ADR-002: Ports-and-adapters structure and a Python / Flask / PostgreSQL stack without an ORM

**Team 16 · Tsala Market · CSI473 Laboratory 9**
**Status:** Proposed. It becomes Accepted when the team confirms assumption A1 (below). Nothing else in this record depends on that confirmation except the choice of language.
**Date:** 9 October 2026
**Relates to:** ADR-001 (refines it, does not replace it)
**Traces to:** `docs/pattern-decisions.md` · `docs/framework-decision.md` · `models/detailed-class-design.md` · `core-operation.md` · `deployment.md` · `failure-recovery.md` · `data-integrity.md`

## Context

ADR-001 fixed the outer shape: one deployable, one relational database, channel adapters over application services, and an in-process worker that keeps a `BucketAggregate` cache current. It did not say how the inside of that deployable is organised, or what it is built with. Laboratory 8 then added constraints that bear on both:

- The database has two roles with different rights: `app` may only read `BucketAggregate` and may only insert into `AuditLogRecord` and `FairPriceCheckQuery`; `worker` writes the aggregate (`deployment.md` §3; DC-10, DC-18, DC-19, DC-22).
- Failure behaviour must be testable without a real outage: a cut connection before commit, a duplicate request, a rollback (`failure-recovery.md` T1–T7).
- Both channels must give identical results and error codes, and the real USSD gateway is unknown and replaces a simulator later (`core-operation.md`).
- Five different changes must lead to the same recompute (DI-5), and the code making a change should not know about the worker.

**Assumption A1 (not verified):** at least some team members can work in Python. The team's strongest language is not known to the author of this record.

## Decision

### 1. Structure

The internal structure is **ports and adapters**, using three named patterns (full reasoning, participants and tests in `pattern-decisions.md`):

| Pattern | Decision |
|---|---|
| **P1 Repository behind ports** | Persistence is reached only through nine small outbound ports, split along the database roles. `AuditLog` has no update or delete method; `QueryLog` has no update method. `Transaction.run` wraps the check-and-log step and the admin-change-and-audit step |
| **P2 Adapter + command object** | Only `UssdCallbackAdapter` knows the gateway's format. Both adapters build a `CheckFairPriceCommand` and call `ICheckFairPrice`. Validation lives in the service side (`FairPriceCheckValidator`), never in an adapter |
| **P3 Domain events + coalescing queue** | Services publish `BucketInvalidated` after commit. A queue coalesces duplicate keys. `AggregateRecomputeWorker` recomputes each key. `DailySweep` is both the ageing mechanism and the safety net for events lost in a crash |

The dependency rule is: adapters call the inbound port; services depend on ports and domain types; domain types depend on nothing outside the domain; infrastructure implements ports and is never imported inward. It is checked automatically in CI.

### 2. Technology stack

| Choice | Decision |
|---|---|
| Language | Python 3.12 or later, type hints checked by `mypy` |
| Web | Flask inside the adapters only; `gunicorn` with **one** worker process and several threads |
| Database | PostgreSQL |
| Database access | Hand-written parameterised SQL through `psycopg` in the repository implementations |
| Ports | `typing.Protocol` classes in `src/interfaces-or-ports/` |
| Wiring | One composition root, no dependency-injection container |
| Tests | `pytest`; repository contract tests run against the in-memory fake **and** a real PostgreSQL |
| Rule enforcement | `import-linter` contracts in CI; Flask importable only in `src/adapters/`, psycopg only in `src/infrastructure/` |
| Dependencies | Declared in `pyproject.toml`, locked with hashes, four direct runtime dependencies, additions justified in `docs/framework-decision.md` §5 |

## Alternatives considered

**Structure.** A single service layer calling a general-purpose data-access class directly, with the worker called from each place that changes data. This is less code, but it hides the database role split, makes the failure tests need a real database, and wires the worker into every service. Strategy for fairness thresholds, CQRS, a Builder for the result, Strategy or Chain of Responsibility for verification rules, and a caching proxy were each considered and rejected with reasons (`pattern-decisions.md` §5).

**Stack.** Python with FastAPI, TypeScript with Express, and Java with Spring Boot were compared against six project-specific criteria (`framework-decision.md` §3). FastAPI was rejected mainly because its automatic request validation returns its own 422 error shape, which clashes with the contract's stable 400/422 meanings. MySQL 8 also meets the database-integrity criterion; PostgreSQL was preferred narrowly, because schema changes can be rolled back inside a migration.

**Explicit rejections.**

| Rejected | Reason | Reconsider if |
|---|---|---|
| **An ORM or entity-mapping layer** (the main rejection) | Mapped objects write any changed column on flush, which hides a violation of DC-22; lazy loading puts database access inside objects that must depend on nothing; `PriceBucket`, `FairPriceCheckResult` and `QueryLogRecord` do not correspond to tables; there are only about fifteen queries to map | More than about thirty distinct queries, schema changing more than weekly, or mapping code taking more time than features |
| A dependency-injection container | About a dozen collaborators in one composition root; a container adds reflection through which a dependency can appear unrecorded | More than about thirty collaborators, or per-request scoping needed |
| SQLite, even for development | No roles or privileges, so DC-18, DC-19 and DC-22 could not be tested | The privilege rules are dropped |
| A message broker or second service | Already rejected in ADR-001 | ADR-001's reconsideration triggers fire |
| An asynchronous web framework | Loads in QS-01 and QS-06 are small; async makes the worker and transaction rules harder to reason about | Measured concurrency exceeds what threads handle |

## Consequences

### Positive
- The database privilege rules (DC-10, DC-18, DC-19) and transaction rules (DC-16, DC-20) are visible in the code's structure, not only in the database.
- Failure tests T3 and T7 run without a database; the same repository contract suite runs against a real PostgreSQL.
- Replacing the simulator with the real USSD gateway changes one class, `UssdCallbackAdapter`.
- The sixth recompute trigger, if one appears, is one more publisher of `BucketInvalidated`, not an edit to every service.
- Exact decimal arithmetic for the half-up P/kg conversion comes with the language.

### Negative
- **About nine interfaces with two implementations each** to keep in step. A fake that behaves differently from PostgreSQL, above all a fake `Transaction` that does not discard writes on failure, would make the rollback tests pass for the wrong reason.
- **Hand-written SQL and row mapping**, with the risk of code and schema drifting apart.
- **In-process events are lost if the process dies between commit and recompute.** A bucket can then serve a stale value until the next sweep, so the sweep interval is a staleness bound, and it is not yet decided.
- **One gunicorn worker.** The recompute worker must run exactly once, so the application cannot be spread across worker processes without the single-active-worker safeguard ADR-001 already flagged. This is the same limitation as ADR-001's highest risk, not an additional one.
- **Flask is synchronous**, so a long recompute must run on its own thread rather than a request thread.
- **A1 is unverified.** If the team is not comfortable in Python, delivery risk rises regardless of how well the design fits.

## Effects on ADR-001

ADR-001 is not yet edited. This record requires three updates to it, listed in `pattern-decisions.md` §6 and `data-integrity.md` §4 (DI-5):
1. `PriceEntry` no longer raises the verified event; services publish `BucketInvalidated` after commit.
2. The worker's triggers widen from one to five (verified, ageing, correction, exclusion, configuration change).
3. A scheduled sweep is added, with its interval decided.

## Evidence that would trigger reconsideration

1. **A1 fails:** the team cannot work comfortably in Python within the first week of implementation. Only the language row of the stack changes; the structure and rejections stand (`framework-decision.md` §7).
2. **QS-01 is missed** on measurement and profiling points at Flask or the layering rather than the design.
3. **The repository contract suite repeatedly passes on the fake and fails on PostgreSQL**, showing the fakes cannot be kept honest.
4. **The single worker process cannot host the recompute worker and request threads together** (ADR-001 trigger 1).
5. **PostgreSQL is unavailable** in the team's lab or hosting environment.
6. **A lost-event staleness incident** shows the sweep interval is too long for the bound the team will accept.

## Risk carried forward

The highest risk from this decision is the **divergence of the in-memory fakes from the real database**. The failure and integrity tests that matter most (rollback, duplicate request, concurrent duplicates) are cheap to run only because of the fakes, so a fake that is too forgiving removes the protection the design was meant to give. The control is the shared repository contract suite, run against both implementations in CI, and keeping T4 (process kill after commit) and the concurrency test T2 as real-database tests.

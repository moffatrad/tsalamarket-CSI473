## Decision 1: Price Entry Verification State Model

# Context
From our use cases (UC-01 - Submit Price, UC-02 - Fair Price Check), we identified that price data must be trustworthy to underpin the Fair Price Check calculation. The project proposal (Section 6a) establishes a verification workflow where entries move from "Community-reported" to "Verified" through corroboration or admin confirmation. We needed to model this state transition in the domain.

# Decision
We modelled the `PriceEntry` class with a `verificationStatus` attribute that can be one of three states: `UNVERIFIED`, `VERIFIED`, or `REJECTED`. A `PriceEntry` transitions from `UNVERIFIED` to `VERIFIED` when either:
- A second independent submission for the same commodity/district/grade/market-level is received within 72 hours and within 15% of the original
- A System Admin manually confirms it

The Fair Price Check calculation **only** uses `VERIFIED` entries from the last 30 days.

# Rationale
- This directly implements **Objective 3**: "Verified vs Community-reported price-tagging and submission workflow"
- The 72-hour corroboration window and 15% tolerance are explicitly defined in the project methodology (Section 6a)
- The 30-day aggregation window is also specified in Section 6a as a validity constraint
- This state machine ensures that `PriceEntry` objects manage their own verification lifecycle, following the Information Expert pattern

# Alternatives Considered
**Alternative:** We considered using a simple boolean `isVerified` flag and storing verification metadata (corroborating entry IDs, timestamps) as separate fields.

**Why rejected:** A boolean flag cannot capture the full lifecycle (unverified → verified → rejected). It also doesn't express the business rule that an entry must meet specific criteria (72-hour window, 15% tolerance) to become verified. The enum-based state model makes these transitions explicit and enforceable in code, reducing the risk of invalid states.

# Consequences
- **Positive:** The verification state is explicit and traceable. The 30-day window rule is enforced at query time rather than requiring manual cleanup of stale data.
- **Trade-off:** Adds complexity to price submission (requires checking for corroborating entries). However, this complexity is necessary to meet the project's trustworthiness requirement.

### Related Artefacts
- **Requirement:** Objective 3 - Verified vs Community-reported price-tagging
- **Use Case:** UC-01 - Submit Price, UC-02 - Fair Price Check
- **Domain Model:** `PriceEntry` class with `verificationStatus` attribute
- **Business Rule:** BR-03 - Only verified entries from last 30 days feed into Fair Price Check
- **Methodology:** Section 6a - Verification (corroboration within 72 hours and within 15%)

## Decision 2: Reference Price Calculation Using Median Instead of Mean

### Context
For the Fair Price Check feature, the system must calculate a reference price to compare against a farmer's offered price. The project proposal (Section 6a) specifies that the reference price should be the "verified market average." We needed to decide which measure of central tendency to use.

### Decision
We calculate the reference price as the **median** of the pooled verified entries (bucketed by commodity × district × grade × market level), rather than the mean. The reference price is the middle value after excluding outliers (entries >1.5× IQR outside Q1–Q3).

### Rationale
- The project proposal explicitly states (Section 6a): "The median is less sensitive than the mean to the small, unevenly distributed samples expected in an early-stage crowd-sourced dataset"
- Outliers (mistyped entries or opportunistic quotes) are common in manual data entry. The median is robust to up to 50% of data being skewed, whereas a single extremely high or low value can distort the mean
- The project explicitly acknowledges "synthetic/anonymised price data" will be used, meaning sample sizes may be small—the median performs better with small samples
- This aligns with the fairness flag thresholds (±10% = Fair, 10-25% below = Below Average, >25% below = Significantly Underpaid), which are more stable when based on a median

### Alternatives Considered
**Alternative:** Using the arithmetic mean of all entries in the bucket.

**Why rejected:** The mean is highly sensitive to outliers. In a crowd-sourced system with manual data entry, a single farmer accidentally adding an extra zero (e.g., entering 150 instead of 15) could skew the average and mislead farmers about fair prices. The project's own risk assessment (Section 8) identifies "inaccurate or malicious crowd-sourced price submissions" as a concern. While the verification workflow mitigates this, the median provides an additional layer of robustness.

### Consequences
- **Positive:** More robust to bad data, even after verification. The result is more trustworthy for farmers making selling decisions.
- **Trade-off:** The median is slightly less familiar to users than "average" (mean). However, the system returns the actual reference price in Pula/kg, and the fairness flag is the primary decision aid—farmers don't need to understand the statistics behind it. The confidence label (High/Medium/Low) provides transparency about data quality.

### Related Artefacts
- **Requirement:** Objective 2 - Fair Price Check feature
- **Use Case:** UC-02 - Fair Price Check (check my offer)
- **Domain Model:** `PriceCalculationService` class responsible for calculating reference price
- **Business Rule:** BR-04 - Reference price uses median (not mean) of verified entries
- **Methodology:** Section 6a - Central tendency and outlier handling
- **Quality Scenario:** Data reliability (trade-off between data freshness and trustworthiness)

## Exit Record (Required by Lab)

### Concept/Responsibility That Moved After Critique

**What moved:** We initially placed the responsibility for calculating the reference price (median calculation, outlier detection, confidence labelling) directly in the `PriceEntry` class during our CRC card session. However, during our consistency review, we realised this was overloading the `PriceEntry` class with calculation logic that belongs elsewhere.

**Why it moved:** We moved this responsibility to a separate `PriceCalculationService` class. The `PriceEntry` class now focuses on representing a single price submission with its metadata (commodity, district, grade, market level, price, verification status, submission date). The `PriceCalculationService` handles:
- Bucketing entries by commodity × district × grade × market level
- Checking the minimum sample size (≥5 entries, ≥2 submitters)
- Outlier detection (1.5× IQR rule)
- Median calculation
- Confidence label generation (High/Medium/Low based on sample size, submitter diversity, and recency)

**How this improves cohesion:** `PriceEntry` is now cohesive—it only manages the state and lifecycle of a single price submission (including its verification state). The `PriceCalculationService` is also cohesive—it only handles aggregation and calculation logic. Neither class is responsible for the other's concerns.

**How this reduces coupling:** The `FairPriceCheck` controller now depends on `PriceCalculationService` (a stable interface) rather than directly accessing and manipulating `PriceEntry` collections. If the calculation methodology changes (e.g., changing the IQR multiplier or moving to a weighted median), only `PriceCalculationService` needs to change. Similarly, if the `PriceEntry` data model changes (e.g., adding a `sourceType` field), the service layer adapts without breaking the controller logic.

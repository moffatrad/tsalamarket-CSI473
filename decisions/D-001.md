# D-001: System context boundary for Tsala Market

**Status:** Accepted
**Date:** 2026-08-10
**Team:** 16 — Tsala Market

## Context

Tsala Market closes the price-information gap between smallholder farmers and
buyers across Botswana's grain, horticulture, and livestock markets. Before
designing internal architecture, the team needed to agree on exactly what
falls *inside* the system versus what remains an external actor or system,
so that later diagrams (DFDs, sequence diagrams, ERD) and the vertical slice
build against a consistent boundary.

Two boundary questions needed resolving:

1. Should BAMB and the telecom USSD/SMS network be modelled as systems
   *inside* Tsala Market, or as external systems the platform integrates
   with?
2. Should the System Admin role be modelled as part of the system (an
   internal service/process) or as a person outside the boundary who
   operates the system through an interface?

## Decision

- **One system boundary**, labelled "Tsala Market — price transparency
  platform," contains all price-lookup, verification, and Fair Price Check
  logic described in the proposal.
- **BAMB** and the **USSD/SMS gateway** are modelled as **external systems**,
  outside the boundary, even though the current semester build will mock
  and synthesise their data rather than integrate live. The context diagram
  documents the target architecture the system is designed against, not
  only what ships this term; treating them as external now avoids a
  boundary redraw when live integration becomes possible.
- **All human roles** — Farmer, Market Vendor/Cooperative Lead, Verified
  Buyer, Extension Officer/Ministry of Agriculture, and **System Admin** —
  are modelled as actors outside the boundary. This includes System Admin:
  administration is treated as an operator interacting with the system
  through an interface, not as internal system logic.
- Every connector between an external actor/system and the boundary is
  two-way and labelled with the data that crosses it (e.g. farmer submits
  an offer and receives a fairness flag in return), reflecting that each
  stakeholder relationship in section 4 of the proposal involves both a
  need and a response from the system.

## Consequences

- Downstream diagrams (DFD level 0, sequence diagrams for the Fair Price
  Check workflow) must treat BAMB and the USSD/SMS gateway as data sources
  arriving through an interface/adapter layer, not as internal modules —
  this keeps the door open for real integration post-semester without
  changing the boundary.
- The mocked/synthetic nature of BAMB and telecom data (per the proposal's
  assumptions and constraints) must be called out explicitly wherever it's
  referenced, since the diagram itself does not visually distinguish mocked
  external systems from eventual live ones.
- System Admin functions (account management, data verification) will be
  designed as an admin-facing interface into the system rather than a
  background service, which has minor implications for authentication and
  UI scope in the vertical slice.

## Alternatives considered

- **Model BAMB/telecom gateway as internal mock modules.** Rejected —
  would misrepresent the target production architecture and require
  redrawing the boundary later when real integration is attempted.
- **Model System Admin as an internal system process** (e.g. an automated
  verification service) rather than a person. Rejected — the proposal's
  stakeholder table (section 4) describes System Admin as a role with
  needs and concerns, consistent with a human actor, not an automated
  component.
